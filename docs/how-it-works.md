# How it works

Three design decisions explain most of this repo. If you only read one document
beyond the README, read this one.

---

## 1. Your evidence is a file, not a prompt

Everything the system claims about you comes from `profile/proof-points.md`.
Nothing else. No model memory, no clever prompt, no inference from your job
titles.

That file is structured so a claim cannot drift:

```markdown
### Metrics
| Metric | Defensibility | Notes |
|---|---|---|
| Purchase completion +30% | Strong | A/B test on live traffic, I ran it |
| Team velocity improved | Weak | shared credit, do not put a number on it |

### What I do NOT have
- Native mobile at production scale
- Managing people
```

The last section is the important one. It is a list of things the system must
never say, and it is checked before output. Without it, a model asked to write
a resume for a mobile role **will** find a way to imply mobile experience,
because that is what makes the text fit.

**If you write this file carelessly, nothing else here helps you.**

---

## 2. Four of the seven score dimensions are locked

Every posting is scored out of 100:

| Dimension | Max | Locked? |
|---|---|---|
| Role title alignment | 20 | no |
| Must-have skills | 25 | no |
| Evidence strength | 20 | no |
| **Seniority** | 10 | **locked** |
| **Domain relevance** | 10 | **locked** |
| **Location and work authorization** | 10 | **locked** |
| **Feasibility and freshness** | 5 | **locked** |

Scoring happens twice: once against your existing resume, once after tailoring.
`scripts/score_guard.py` compares the two and **rejects the result** if a locked
dimension improved.

The reason is simple. Rewriting a resume does not give you more years of
experience, does not move you to another city, and does not make a month-old
posting fresh. A model scoring its own work will raise those numbers anyway,
gradually, because a higher score feels like a better answer. A script does not
care how the answer feels.

Every unlocked increase must also carry the **exact resume line** that justifies
it and a reason, or the guard refuses it:

```json
{ "dimension": "must_have_skills", "from": 21, "to": 23,
  "resume_line": "Prototyped the correction flow in React after static mocks...",
  "reason": "They ask for a natural prototyper who does not just design static mocks." }
```

Run it yourself:

```bash
python3 scripts/score_guard.py applications/<job>/score-breakdown.json
```

---

## 3. The agent reads as little as possible

Token cost is a design constraint, not an afterthought.

- `AGENTS.md` is a routing table. It tells an agent which file to open for which
  task and explicitly says not to load the others.
- `TRACKER.md` is **generated by a script**, not a model, and answers status
  questions without opening a single application folder.
- Resumes are read from pre-extracted markdown in `profile/resumes-md/`. The
  `.docx` is only opened when a final file is produced.

A status question that would otherwise cost thousands of tokens costs none.

## Browser automation: why no Playwright

`scripts/ats_fill.mjs` and the adapters talk to Chrome over the **DevTools
Protocol** directly, with no browser-automation library:

```bash
# start Chrome with the debugging port open
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome \
  --remote-debugging-port=9222
```

Three reasons:

1. **No dependencies.** This repo installs nothing. `npm install` does nothing
   because there is nothing to install. That matters for something you will run
   against pages holding your personal data.
2. **It attaches to your real browser session**, already logged in. Playwright
   launches a fresh profile, so every ATS asks you to sign in again, and some
   flag the automated browser outright.
3. **Scraping a job posting rarely needs a browser at all.** Most ATS platforms
   have a public JSON API, which is faster and more reliable:

   | Platform | Endpoint |
   |---|---|
   | Greenhouse | `boards-api.greenhouse.io/v1/boards/{board}/jobs?content=true` |
   | Ashby | `api.ashbyhq.com/posting-api/job-board/{board}` |
   | Lever | `api.lever.co/v0/postings/{company}?mode=json` |

   Use `first_published` on Greenhouse, not `updated_at` — the latter is a
   last-modified stamp and whole boards refresh at once, which will make every
   posting look new.

**If you prefer Playwright, swap it in.** The adapters in
`scripts/ats_adapters.mjs` are the only place that touches a page, and they are
plain functions over a DOM. Nothing else in the repo knows how the page was
reached.

## The submit boundary

`scripts/ats_fill.mjs` fills a form, reads every value back to confirm what the
page actually holds, and then **stops**. It does not click submit, ever, at any
score.

It also refuses outright to touch credential, OTP, government ID and payment
fields. Those are yours to type.

This is the one rule worth keeping if you change everything else. The failure
mode of an auto-applier is not that it submits a bad application; it is that it
submits fifty before you notice.

---

## Verify the output, always

Two real failures from building this:

- A fill script reported a successful selection while having chosen the wrong
  gender option. The log said success.
- A page-count check passed on a resume that was two-thirds empty.

Scripts report success on output that is wrong. Render the PDF and look at it.
Read back what a form field actually holds. When grepping extracted PDF text,
flatten the line wrapping first or you will get false negatives:

```bash
pdftotext file.pdf - | tr '\n' ' ' | grep -o "what you expect"
```
